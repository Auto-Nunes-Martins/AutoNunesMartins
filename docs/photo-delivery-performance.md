# Public photo delivery diagnostics

Public vehicle photo responses expose a bounded `Server-Timing` header on successful image responses and conditional 304 responses. The website proxy forwards only the numeric photo-stage allowlist. No credentials, SQL, database hosts, storage keys, paths or user data are included.

| Metric                                 | Meaning                                                                                                                                                                                                                                       |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `photo-check`                          | Wall-clock time awaiting the live public-availability and approved-photo query, including any shared in-flight wait. Not database execution time alone.                                                                                       |
| `photo-cache-hit` / `photo-cache-miss` | Pixel cache outcome; zero duration is a marker, not a measured lookup duration.                                                                                                                                                               |
| `photo-manifest`                       | Selecting the derivative. Thumbnail widths (320, 384, 800) use a known in-memory manifest or their deterministic path without fetching a manifest. Larger widths retain the manifest lookup. Absent on a pixel cache hit or original request. |
| `photo-storage`                        | Downloading and validating the selected file, including original fallback if required. Absent on a pixel cache hit.                                                                                                                           |
| `photo-total`                          | Total route preparation from availability lookup through ready image bytes. Includes the stages above; do not add it to them. Excludes internet transfer and website proxy overhead.                                                          |

Read the header in the image request's Network response headers/Timing panel, or in an HTTP client. Each request reports its own current timings; this is not a public historical log. Deployment is required before the public domain exposes these metrics.

Cold thumbnail reads request the exact private derivative directly. Delivery checks MIME, byte/pixel limits, complete WebP RIFF/chunk boundaries and expected static-image dimensions; an invalid or missing derivative falls back to the original. Full pixel decoding is performed during generation, before uploading each generated file, rather than repeating `sharp.stats()` on every cold delivery. Existing derivatives were produced by the same private encoder and retain the lightweight delivery checks; there is no backfill or recompression in this change. Structural checks detect truncated containers, not arbitrary corruption of an otherwise structurally valid compressed payload. Temporary storage errors are returned rather than triggering an additional download. A complete derivative from an interrupted batch is individually usable; the manifest still records whether the entire generation batch completed. Live authorization and in-flight sharing remain in place. Shared waiters report their own total and cache-miss marker, but only the owning request reports the storage stages.

## Initial thumbnails and bounded retention

The detail query starts best-effort preparation of the first nine **320px base thumbnails** from the already-approved paths. The JSON/HTML response never waits for these downloads. A process-wide pool allows two speculative reads and up to 36 queued paths, discarding work that waited over five seconds. Actual image requests share an in-progress read. Speculation never falls back to a large master. Every later public image request still checks live authorization, even if preparation has completed.

The HTML head also advertises nine responsive image preloads using exactly the thumbnail `srcset` and `sizes`. The browser can select 384/800px or another required resolution without a quality cap; those larger choices are not speculatively downloaded by the server. The first nine displayed thumbnails use normal browser priority, the main photo retains high priority, and later thumbnails remain lazy/low priority. Warm in-document thumbnail reuse omits these preloads.

The pixel cache remains **12 MiB per backend process**, now shared dynamically. Derivatives up to 800px and 512 KiB each retain a soft 4 MiB reservation and ten-minute TTL; other eligible images retain a one-minute TTL. Either class can borrow unused capacity. At pressure, LRU eviction protects the thumbnail reservation from gallery entries. The cache is capped at 1,024 entries. Original fallbacks do not qualify for the reservation. Deletion/regeneration invalidates every width and queued preparation; this is not a permission cache. In-flight buffers, decoder working memory and other caches are separate from the 12 MiB retained-pixel budget. Successful photo responses identify this policy as `X-Photo-Cache-Policy: shared-v1`.

The website streams authorized image responses when the backend supplies an unencoded body with a valid Content-Length within the 20 MiB limit. It validates MIME first and checks each chunk and final length, propagates cancellation, and never forwards more than the declared bytes. A late truncation fails the stream rather than changing the already-sent status. Responses without a usable length retain the buffered fallback. `X-Photo-Delivery: stream-v1` identifies streamed delivery. This removes a second full-image buffer; it does not bypass storage validation or live availability checks.

When measuring after deployment, distinguish a first visitor with server-prepared pixels from a truly cold storage read. Opening the detail page can warm its base thumbnails before the timing request. Do not describe a `photo-cache-hit` as cold, or compare a hit to an old storage miss as an equivalent scenario. Network timings alone also do not measure when the thumbnail strip became visible.

Compare first reads, immediate repeat reads and conditional requests separately, using the same image and width. Keep live authorization for every request and 304, the existing private revalidation policy, byte limits, MIME validation and immutable pixel identity. These diagnostics do not resize or recompress photos.

Before instrumentation, short public samples showed about 173 ms to obtain current photo authorization versus 63 ms for the no-database health response. Warm image response headers were about 172 ms through the backend versus 175 ms through the website. These are external observations, not an exact production database breakdown. Separate local-process measurements must not be presented as production-internal timings.
